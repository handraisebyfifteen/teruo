# teruo — 設計書B（システム仕様）

> English translation: [teruo-design.en.md](teruo-design.en.md)

キッチンカー・屋台向けの在庫管理エージェント。
設計書A（Tier 1 実装）の上位にあたる、システム全体の仕様。
デモの題材（ケバブ）と、システムの仕様を分けて記載する。

最終更新: 2026-09-01（追記反映: 消費型3分類・係数の上限・原則10/12）

## 名前について

**teruo**（英字小文字。文頭でも teruo）

由来は英語の tell。
このシステムは計算はするが、動かない。教えるだけ。
開店前に言う、営業中は黙る、締めに報告する。すべて tell。

日本語の人名「照男・輝雄」とも重なり、「教える・照らす」の両方に読める。

- 表記ゆれ禁止: Teruo / TERUO / テルオ は使わない
- by fifteen の既存プロダクト（handraise、DeliSpot、暗号ちゃん、tabenote）と同じ英字小文字の系列
- 商標未確認。ハッカソン提出には支障ないが、譲渡・商品化の前に J-PlatPat で確認すること
- GitHub のリポジトリ名は teruo が取得済みの可能性が高い。teruo-agent 等で代替

## 0. このシステムが効く店の条件

業種名では判定しない。以下2つが揃うほど価値が出る。

1. **人の手で量が変わる**（削ぐ、すくう、かける、盛る）
2. **1つの材料が複数の商品にまたがる**（多対多）

| 業種 | 品目数 | 誤差 | 商品との関係 | 適性 |
|---|---|---|---|---|
| ホットドッグ | 少 | 小 | 1対1 | 低（数えれば分かる） |
| 棒アイス | 中 | なし | 1対1 | 低 |
| スクープアイス | 多 | 大 | ほぼ1対1 | 中 |
| ケバブ | 中 | 大 | 多対多 | **高** |

同じ「アイス屋」でもスクープ式と棒アイスで性質が変わる。
業種テンプレートは作らない。作り方を聞いて判定する。

## 1. システムの原則（11項目）

### 原則1 — 理論値を置いて、実測で直す

係数も unit_weight も同じ構造。目安を置いて動かし、実測が来たら修正する。
最初から正確である必要はない。

### 原則2 — 何が正か（優先順位）

```
棚卸しの実測 ＞ 仕入れの実測 ＞ 目安値からの計算
```

上位が来たら下位を上書きする。迷ったら実測。

### 原則3 — 計算は Python、判断は AI

数値計算を LLM にさせない。
AI がやるのは「何を数えてもらうか」「これは異常か」の判断のみ。

### 原則4 — 構造を変える操作と、日々の入力を分ける

前提：この端末を触るのは店主だけではない。
ただし「誰でも」ではない。売上や棚卸しを入力するのは、在庫を任されている上位スタッフ。
入ったばかりの人は触らない。

| 層 | 誰 | できること |
|---|---|---|
| 店主 | オーナー | 全部。構造変更には合言葉が要る |
| 在庫担当 | 任された上位スタッフ | 売上・棚卸し・仕入れの入力 |
| 一般 | それ以外 | 触らない |

単位・レシピ・品目の構成を変える操作は、店の設定そのものを書き換える行為であり、
在庫担当が「なんとなく」触れる場所に置いてはいけない。

| 操作 | 誰が | 実行前 | 実行後 |
|---|---|---|---|
| 売上を入れる | 在庫担当 | — | — |
| 棚卸しを入れる | 在庫担当 | — | 異常値の時のみ通知 |
| 仕入れを入れる | 在庫担当 | — | — |
| レシピの量を変える | 店主のみ | 合言葉＋確認 | 通知 |
| 単位を変える | 店主のみ | 合言葉＋確認 | 通知（変更前後の値つき） |
| 品目を追加する | 店主のみ | 合言葉＋確認 | 通知 |
| 商品を削除する | 店主のみ | 合言葉＋確認 | 通知 |

#### 2段構えにする理由

合言葉は入口の鍵で、通知は後から気づく手段。
役割が違うので両方要る。

合言葉は必ず漏れる。店主が忙しくて従業員に教える、人が入れ替わって全員が知っている、
という状態は現実には起きる。その時に残る最後の防波堤が通知。

実装は、初回カウンセリング時に店主が設定用の合言葉を決め、
構造変更の操作でのみそれを求める（アカウント認証は今回は作らない）。

#### 通知の中身

```
【設定が変更されました】
2026-09-01 14:32

ケバブサンドのレシピ
  ケバブ肉（チキン） 75g → 90g

心当たりがない場合はご確認ください。
```

- **変更前と変更後を両方書く。**「変更されました」だけでは何が起きたか分からない
- 変更を止める機能は作らない。気づける状態にすることが目的
- 元に戻す操作は、店主が手で行う（history に変更前が残っているため可能）

#### 通知の送り先

| 手段 | 今回 |
|---|---|
| メール | 採用（実装が軽い。店主のアドレスを1つ登録するだけ） |
| LINE / Slack | 見送り（連携の手間が締切に合わない） |
| アプリ内通知 | 見送り（画面がないため） |

カウンセリング段階7で、合言葉と一緒に通知先アドレスを登録する。

※ 実装優先度は中。Tier 1・登録ツールが通った後に着手する。
　 間に合わない場合は、通知の代わりに history への記録のみとし、
　 「設定変更の履歴」を get_stock_status から見られる形にする（これは軽い）。

#### 単位変更の具体的な扱い

- 同種別（g → kg）は換算する
- 種別をまたぐ（g → 本）は換算しない。棚卸しで入れ直す
- 変更前の単位・在庫・日時を history に必ず残す
  → 過去の数値が「どの単位で記録されたものか」を後から追えるようにする
- 変更後は、その品目の coefficient を 1.0 に戻し、育成期として扱い直す
  → 単位が変われば係数の意味も変わるため、引き継いではいけない

### 原則5 — 消さない

- 品目は削除しない。active: false で隠す
- history は何があっても消さない
- 商品の削除は確認必須

### 原則6 — 分類は業種で決めない。作り方で決める

「ケバブ屋だからこの構成」と決め打ちしない。
「盛る量が変わりますか」の一問で tier を決める。

### 原則7 — 出店形態でデータを分ける

イベント出店と単独出店は、見込みの立てやすさが違う。

| | 母数 | 競合 | 予測の確度 |
|---|---|---|---|
| イベント | 読める（来場者数が事前に分かる） | 主催が調整 | 高い |
| 単独（マルシェ等） | 読めない | いるかも不明 | 低い |

同じ「出店」だが、混ぜて平均を取ると両方外れる。
記録時に一択で選ばせる（1秒で済む）。平均は別々に持つ。

仕込みの量は「気合の量」であり、会場の規模を表している。
イベントで多く仕込むのは正常。単独出店で仕込みが多い日だけが読み違い。
仕込み量を単独で判断材料にしない。必ず出店形態とセットで見る。

### 原則8 — 守るのは在庫だけ。売上の見込みには口を出さない

- 在庫の残量は**辛めに見る**。切れる予測は早めに出す
- 売上の見込みは**辛くしない**。売れるかどうかは店主の領分

「今日は行ける」と思っている人に対して、在庫計算まで同じ楽観で回すと、
外れた時に何も残らない。だが売上まで悲観的に言うのは越権。

### 原則9 — 学習中であることを最初に伝える

頻度も係数も、2〜3回で掴める。だが掴むまでは外れる。

外れてから「まだ学習中でした」と言うのは言い訳になる。
先に言っておくから信用される。

```
初回「最初の1〜2週間は、こちらが数え方を覚える期間です。
     数字は参考程度に見てください。
     何度か棚卸しをしてもらえれば、精度が上がっていきます」
```

学習の対象は、係数だけでなく棚卸しの適切な頻度そのものも含む。
「週1で数える」と決め打ちせず、その品目が何回で安定したかで判断する。

#### 「学習中」には期限を設ける

1ヶ月経っても「学習中です」と言い続けるなら、それは学習していないのと同じ。
そして「学習中」は言い訳の逃げ道になる。
数字が外れても済ませられてしまう。

- 期限は **2週間、または棚卸し5回。どちらか早い方**
- 期限を過ぎたら、精度が上がっていなくても「学習中」とは言わない
- 代わりに**なぜ安定しないか**を報告する

```
×「まだ学習中です」          ← 言い訳

○「チキンの数字が安定しません。
   考えられるのは、削る人が日によって違う、
   棚卸しのタイミングがまちまち、のどちらかです」  ← 情報
```

#### 途中経過を出す

終わりが見えない学習中は不安なだけ。残りを見せる。

```
「学習中です（棚卸し 2回目 / 5回）」
```

### 原則10 — 不足を人に紐づけない

理論値の stock はマイナスになりうる。それはバグではなく、係数が育っていない証拠。

現場では、不足分を個人が補填する悪習がある。
**teruo の数字がその根拠に使われる状態を作ってはいけない。**

#### 理由は2つ。倫理だけではない

**1. 数字の根拠が不正確。**
校正前の理論値なので、その差分自体に根拠がない。
係数が正しくなれば、そのマイナスは遡って消える。
**校正で消えるマイナスは、そもそも損失ではなかった。**

**2. 入力者が不利になるシステムは、正しい入力が得られない。**
打った数字が自分の負担になると分かれば、正直に打たなくなる。
棚卸しを多めに申告する、売上を少なく打つ、打たない日を作る。
そうなると係数はでたらめを学習し、teruo は使えなくなる。
**これは運営上の実利の問題。**

#### 実装

| 記録する | 記録しない |
|---|---|
| 入力の時刻 | **誰が入力したか** |
| 棚卸しの値と、その前後の係数 | **個人ごとの不足額** |
| 変更前後の値（原則4） | |

時刻は残す。「その日のどの入力から係数が動いたか」までは追える。
誰かは店主がシフト表と突き合わせれば分かる。
**teruo が名指ししないだけで、追跡は可能。**

teruo 自身が個人別の不足台帳を持つと、それが請求書として使われる。それだけを避ける。

#### マイナス時の扱い

**0 に丸めない**（`max(0, stock)` を書かない）。
マイナスは「理論値が実測より多く見積もっていた」という情報であり、
0 に丸めると係数を直す材料そのものが消える。原則5に反する。

**エラーで止めない。** 営業中に売上が打てなくなる。teruo が現場を止めてはいけない。

内部では負値のまま保持し、表示だけ変える。

| | 内部 | 表示 |
|---|---|---|
| 通常 | 8,500 | 「8,500g」 |
| マイナス | **-500 のまま保持** | 「実測が必要です」 |

負の在庫は物理的にありえないため、
**数字を出した瞬間に「壊れてる」と受け取られる。**

```
「チキンの理論値が在庫を割りました。
 実際にはまだ残っているはずです。
 こちらの計算が少なく見積もっていました。

 締めに一度、量ってもらえますか」
```

謝らない。理論値は仮置き（原則1）なので、ずれるのは想定内。
**「壊れました」ではなく「情報が足りません」。**

### 原則12 — 端末の外の数字と突合

（番号は追記元の設計書に従う。原則11は欠番）

#### 攻撃面としての係数学習

teruo の中心機能が、そのまま攻撃面になる。

```
1. 棚卸しで実量より少なく申告する
2. teruo は「理論値より減っている」と判断する
3. 係数が上がる（75g → 85g）
4. 以降、1食あたり10g多く消費することが「正常」になる
5. teruo は何も言わない。「むしろ安定しました」と報告する
```

**一度学習させれば、その後の抜き取りは見えなくなる。**
一度に大きく動かすより係数を少しずつ育てるほうが安全、という構造。
分かっている輩ほど捕まらない。

係数の上限（第2章）が、この経路への直接の防御になる。

#### 紙類との突合

第2章に既にある一手の実装。

> 紙類・容器はレシピに含める。係数が動かないので、肉の係数が正しいかの基準線になる。

count 型は係数が 1.0 で固定される。**紙の消費数 = 実際に出た食数。**

| 観測 | 意味 |
|---|---|
| 肉の係数が上がった ＋ 紙も同じだけ増えた | 本当に食数が増えている |
| **肉の係数だけ上がった ＋ 紙は変わらない** | **食数は同じなのに肉だけ減っている** |

ただし**紙も一緒に持ち出せば、この突合は破れる。**
仕組みを理解している輩には有効でない。
そして在庫担当は上位スタッフであり、理解している側にいる。

#### 通らない数字は3つ

在庫も紙も、同じ端末から同じ人が入力する。同時に整合させられる。
端末の中だけでは通らない数字が要る。

| 系統 | 出どころ | 端末内で操作できるか |
|---|---|---|
| 在庫 | 棚卸し（自己申告） | できる |
| 紙 | レシピ経由の理論値 | できる |
| **売上金額** | **レジ・現金** | **できない** |
| **仕入れ** | **業者の伝票** | **できない** |
| **月次の積算** | **月次** | **できない** |

肉を抜く → 食数を減らして申告 → 売上金額が減る → 現金が合わない。
金だけ合わせようとすると、在庫が合わない。**どちらかは必ず合わない。**

#### 月次で見る

閾値の内側に潜り続ける手口は、日次では原理的に検出できない。

```
2g/食 × 100食 = 200g/日   ← 上限4gの内側。単発では絶対に出ない
× 25日 = 5kg/月           ← ホール半分
```

| 見る単位 | 検出できるもの |
|---|---|
| 1日 | 大きな一発 |
| **1ヶ月** | **閾値の内側で継続的に抜く手口** |

```
「今月チキンを 30kg 仕入れ、理論消費は 25kg。
 在庫は 2kg。3kg が説明できていません」
```

日次では出てこない差異。**仕入れは業者側に控えが残るため、店内で完結しない。**

#### teruo は疑わない。見逃さないだけ

teruo は原因を分けられない。
記録漏れ・廃棄の未記録・抜き取りは、すべて同じ「理論値より少ない」として現れる。
**分けられないものについて、片方を断言しない。**

言うのは「事実」と「幅の異常」だけ。

```
「チキンの差が、盛り方で説明できる範囲を超えています。

 100食で 800g。この幅は盛り付けのブレでは出ません。
 仕入れか売上の記録漏れがないか、ご確認ください」
```

どう動くかは店主の領分（原則8）。原則4の通知と同じ、**気づける状態にすることが目的。**

#### 止められないもの

**店主自身による構造変更。**
合言葉を持つ人は止まらない。原価を過大に見せることは技術的に可能で、
原則4の通知は自分に届くため意味を持たない。

ただそれは teruo の管轄外でもある。
騙す相手は teruo でも在庫担当でもなく、税務署か買い手。

**`history` に変更前後をすべて残す**（原則5）。
teruo はリアルタイムに止めないが、後から遡って読める。
**止めないが、消さない。**

防げるふりをしない。「防げない」と書いておく。

## 2. データ構造

### 品目（items）

```json
{
  "id": "meat_chicken",
  "name": "ケバブ肉（チキン）",
  "tier": 1,
  "unit": "g",
  "unit_type": "weight",
  "consumption_type": "weight",
  "purchase_unit": "本",
  "unit_weight": 10000,
  "stock": 8500,
  "coefficient": 1.0,
  "last_counted": null,
  "count_history": [],
  "active": true
}
```

- unit_type は weight / volume / count のいずれか
  → コード内に「g」を直書きしない。後から oz を足せる形にする
- consumption_type は count / weight / unit の3分類（後述）。
  unit_type（単位の種別）とは別の軸で、**消費の数え方**を表す
- purchase_unit と unit_weight は任意
  → 仕入れ単位と消費単位が同じ品目（ピタパン、ナプキン）には持たせない
- unit_weight は目安値であり固定値ではない（原則1）
- coefficient は必ず 1.0 から始める。店主に決めさせない
  （ユニット型のみ例外。初期値は置かず、最初の使い切りで確定する）
- count_history は棚卸しの記録。頻度判定に使う

### 消費型（consumption_type）による3分類

tier 1/2/3 は「誤差が出るかどうか」の軸。それとは別に、
**消費の数え方そのものが品目によって違う。** 軸がもう1本要る。

ソースを g で管理するのは実態に合わない。
業務用は1本・1パックで入る。中身が何gかは誰も測っていない。
手作りの場合、1回に仕込む量は毎回同じ。
**「20g × 何食」ではなく「1本で何食もつか」が現場の数え方。**

| consumption_type | 例 | 係数が表すもの | 係数の学習 |
|---|---|---|---|
| count | ピタ、ナプキン、棒もの | — | **なし。1.0 固定** |
| weight | 肉、ライス、キャベツ | 1食あたりの実消費量 | 棚卸しの差分から |
| unit | ソース、油、調味料 | **1ユニットが何食分か** | **使い切った時点で確定** |

数えて分かるものに係数は要らない（第0章の適性表と同じ理屈）。

#### ユニット型の学習

途中経過は測れない。開封中のボトルの「残り3割」は分からない。
代わりに**切り替わった瞬間だけは確実に分かる。**

```
1本目: 開封 → 48食で空
2本目: 開封 → 52食で空
3本目: 開封 → 50食で空

→ 1本 ≈ 50食。残り1.5本ならあと75食分
```

曖昧な中間値を扱わず、**確定した事実（空になった）だけで学習する。**
重量型より正確で、実装も軽い。

#### 測れないことと、サボれることは別

「使い切るまで分からない。だからバレても仕方ない」と読んではいけない。

少しずつ抜く手口も見える。重量型だと 3〜4g/食 に収まらない。
ユニット型も同じ枠に収まる。1本が50食なら、48〜52食の幅。

`4本目 → 30食で空` が出たら、それはソースの性質ではない。
こぼしたか、別用途に使ったか、記録が漏れているかのどれか。
**「見えている」だけで抑止力になる。**

#### データ構造の追加（ユニット型）

```json
{
  "id": "sauce_yogurt",
  "name": "ソース（ヨーグルト）",
  "consumption_type": "unit",
  "unit": "本",
  "coefficient": 50.0,
  "sales_count": 1250,
  "opened_at_sales_count": 1250,
  "unit_history": [48, 52, 50]
}
```

- `opened_at_sales_count` — 開封時点の累計食数。
  空になった時点の累計との差が、そのまま「1本で何食もったか」になる
- `unit_history` — 過去の実績。上限判定の基準に使う
- `sales_count` — その品目を使った累計食数（実装用のカウンタ）

#### 同じ野菜でも同じ型ではない

キャベツと玉ねぎ・トマト、同じ「野菜」でも性質が違う。

以下はあくまで傾向であって、決め打ちではない。
キャベツを中子で数える店もあれば、トマトを刻んで量って盛る店もある。
**品目名から型を推定するコードを書かない。**

| | 数え方 | 型 |
|---|---|---|
| キャベツ | 千切りにして山から盛る。量が変わる | weight |
| 玉ねぎ・トマト | **1個から何食分か、が決まっている** | unit |

トマト1個を8枚に切り、1食に2枚使うなら、1個で4食。
**盛るのではなく、切る。** 切り方のブレは少ない。

これはソースと同じ構造。「1個で何食分か」を学習する。

#### 中子（なかご）を1とする店

仕込んだものをホテルパン・コンテナに入れ、**その1杯を単位にする**運用がある。

```
玉ねぎ 中子1杯 → 60食
トマト 中子1杯 → 45食
```

回数で数えたら、コンテナが単位になる。
**仕込みの単位がそのまま在庫の単位。** ユニット型でそのまま扱える。

どちらが正かは店による。同じ玉ねぎでも、
個で数える店と中子で数える店があり、**teruo が決めない。**
決めるのはカウンセリングの段階5（第3章）。

### 係数の更新式（平滑化）

棚卸し1回から得られる実測係数は、

```
実測係数 = 現在の係数 × (実消費 ÷ 理論消費)
```

だが、これをそのまま採用すると**日ごとの手のブレ（±5%程度）を全量追いかけて振動する**
（収束シミュレーション tests/simulate_convergence.py で確認済み。振れ幅 最大±5%）。

そこで実測に半分だけ寄せる:

```
新しい係数 = 現在の係数 + 0.5 × (実測係数 − 現在の係数)
```

- 振れ幅は半減し（±2.6%）、収束は棚卸し3〜5回で変わらない
  → 原則9の「学習中は棚卸し5回まで」は実測と整合する
- 実測1回を全面採用しない理由: 実測が正なのは「その日の残量」であって
  「明日以降の手」ではない。1日分のブレまで学習しない

### 係数の上限

盛り方・削り方のブレには物理的な上限がある。
**1食あたり 3〜4g。** それ以上は手が気づく。

100食売った日の理論上の最大差は 300〜400g。
それを超える差は、盛り付けでは発生しない。

| 型 | 上限 |
|---|---|
| count | 係数が動かない |
| weight | **レシピ値 ±4g/食** |
| unit | **過去実績（unit_history）の ±20%** |

ユニット型は初期値が動かないため、固定値を置けない。
3本ぶんの実績が出てから幅を引く。それまでは上限判定を行わない。

#### 上限に達した時の挙動

**学習を止める。** 自動で超えない。

```
「チキンの係数が、盛り付けで説明できる範囲の上限に達しています。
 これ以上は自動で調整しません。

 レシピそのものの見直しが必要かもしれません」
```

レシピの変更には合言葉が要る（原則4）。
**日々の入力が、係数を経由してレシピを実質的に書き換える迂回路を塞ぐ。**

#### 学習終了時に差を見せる

原則9で「最初の2週間は外れます」と宣言している。
それは信頼のために正しいが、同時に「学習中で説明がつく」窓を作っている。
人が入れ替わる時期とも重なる。

学習終了時、初期値と確定値の差を必ず表示する。黙って確定させない。

```
「学習が終了しました。
 チキン: 75g → 82g（+9%）

 この幅でよろしければ、一度ご確認ください」
```

### 商品（products）

```json
{
  "id": "kebab_sand",
  "name": "ケバブサンド",
  "price": 600,
  "recipe": [
    { "item_id": "meat_chicken", "qty": 75 },
    { "item_id": "pita", "qty": 1 },
    { "item_id": "cabbage", "qty": 30 },
    { "item_id": "sauce_yogurt", "qty": 1 },
    { "item_id": "wrap_paper", "qty": 1 },
    { "item_id": "napkin", "qty": 1 }
  ]
}
```

紙類・容器はレシピに含める。係数が動かないので、肉の係数が正しいかの基準線になる。

ユニット型の材料の qty は「1食で使う食分」（通常 1）。
量（g）ではなく、係数（1ユニット＝何食分）側が実態を持つ。

### 売上記録（history）

```json
{
  "recorded_at": "2026-09-01T20:14:00+09:00",
  "venue_type": "event",
  "product_id": "kebab_sand",
  "quantity": 35
}
```

venue_type は event / solo の2択（原則7）。
記録時に一択で選ばせる。平均はこれで分けて持つ。

## 3. 初回カウンセリング（7段階・10分以内）

途中でやめても、そこまでが保存される。完璧に埋めさせない。

### 段階1 — 店の輪郭

```
「どんなものを売っていますか」
「メニューをひと通り教えてください」
```

業種名を聞いても、内部では決め打ちしない（原則6）。

### 段階2 — メニューごとの中身

```
「ケバブサンドには何が入りますか」
→ ピタ、肉、キャベツ、ソース

「量が決まっているものはありますか」
→ 肉75g

「残りはこちらで置いておきます。キャベツ30g、ソース20g。後で直せます」
```

**空欄で止めない。** AI が埋めて先に進む。
埋める値は店の性格を踏まえる（日本の屋台なら量は控えめ）。

### 段階3 — 誤差を聞く（tier 判定）

```
「盛り付ける時、毎回同じ量になりますか。人によって変わりますか」
```

- 変わらない（袋から出す、1本渡す）→ 係数固定 1.0
- 変わる（すくう、削ぐ、かける）→ 係数が動く / Tier 2

### 段階4 — 見落としを拾う（★要拡充）

店主は材料しか言わない。エージェントから具体的に聞きにいく。
「他にありますか」では出てこない。

```
「揚げ物はありますか」→ 油
「持ち帰りの容器は」→ 容器、袋、ナプキン
「割り箸やスプーンは」
```

※ ここのリストが本システム最大の資産。現場経験から拡充すること。

### 段階5 — 仕入れの単位と、数える単位

```
「肉はどう仕入れますか。塊ですか、パックですか」
→ 塊 → 「1本だいたい何kgですか」→ unit_weight に入る
```

仕入れの単位だけでは足りない。仕入れの単位と、数える単位は違う。

```
「玉ねぎはどう仕入れますか」        → 現行のまま。袋、箱
「使う時は、何を1として数えますか」 → 追加

  1個ずつ         → unit = 個
  中子・バット単位 → unit = 中子
  刻んで量る       → weight
```

この一問で consumption_type と unit が同時に決まる。
段階3（誤差を聞く tier 判定）と並ぶ、**分岐の要になる質問。**

### 段階6 — 現在庫

```
「今ある分を教えてください。だいたいで大丈夫です」
```

**正確さを求めない。** 求めると始められない。棚卸しで直る。

### 段階7 — 合言葉と通知先を決める

```
「レシピや単位を変える時だけ使う合言葉を決めてください。
 日々の入力には要りません。
 スタッフの方が誤って設定を変えてしまうのを防ぐためです」

「設定が変わった時にお知らせするメールアドレスを教えてください。
 合言葉を知っている人が増えても、変更に気づけるようにするためです」
```

原則4の権限分離に使う。ここだけは店主本人に決めてもらう。
メールアドレスは Replit Secrets ではなく state.json に持つが、
リポジトリ公開時にデモ用の架空アドレスに差し替えること。

## 4. 棚卸しの頻度

システムが一律に決めない。店主にも決めさせない。必要な時だけ頼む。
毎日全部数えさせたら3日でやめる。

### 育成期（最初の5回程度）

営業後に毎回お願いする。理由を添える。

```
「まだ覚えている途中なので、今日も数えてもらえますか」
```

### 安定後

係数の変動が収まったら週1に落とす。

```
「ソーセージは安定したので、来週まで数えなくて大丈夫です」
```

### 臨時

- 理論値と実測が急にズレた
- 新しい人が入った
- 在庫が切れそう

### 全部を一度に数えさせない

20品目あっても、その日に頼むのは2〜3品目だけ。
何を数えるか選ぶのがエージェントの仕事。

## 5. 報告のタイミング

**営業中は原則、黙る。**

### なぜ営業中に言わないか

在庫が切れるのは、必ず一番忙しい時。その最中に言われても対応できない。
対応できない情報は邪魔でしかない。

そしてピークが引いた瞬間も暇ではない。
次の山に向けた**「装弾」の時間**（肉を刺す、野菜を切る、ソースを詰める）であり、
むしろ手が空かない。「引いたら入力」は成立しない。

### 3つのタイミング

| いつ | 何を言うか |
|---|---|
| 開店前 | 今日の見込み。足りないものの予告 ← **ここが本命** |
| 営業中 | 原則、黙る。切迫時のみ「あと10食分」と事実だけ |
| 締め | 実績、棚卸しの依頼、発注 |

開店前が唯一、判断できる時間。手が空いていて、まだ買い足せる。
営業中は手遅れ、締めはもっと遅い。

### 営業中に言っていいこと

事実のみ。判断を求めない。

```
○「ソース、あと10食分です」
×「ソース、あと10食分です。発注しますか？」
×「どうしますか？」
```

あと10食と分かれば、その場でできることがある
（量を減らす、メニューから外す、告知する）。判断は一瞬で済む。

### 入力のタイミングは強制しない

打てる時に打つ。打てなければ締めでいい。
システム側が入力の頻度に合わせて振る舞いを変える。

```
締めの入力しかない日が続いたら
→「日中は打てないようですね。締めだけで大丈夫です」
→ 締めのデータから翌日の見込みを立てる方に切り替える
```

「その都度入れてください」と要求しない。

## 6. 育成フェーズの明示

導入直後と2週間後では信頼度が違う。それを店主に見せる（原則9）。

```
1週目「学習中です（棚卸し 2回目 / 5回）。数字は参考程度に見てください」
2週目「チキンの係数が安定してきました」
3週目「在庫、そろそろ切れます」← ここから発注提案を始める
```

実装は count_history の件数と係数の変動幅を見るだけ。

「学習中」は 2週間 / 棚卸し5回で打ち切る（原則9）。
それを過ぎたら、学習中とは言わず、安定しない原因を報告する。

## 7. 同時書き込み

前提：在庫担当が2人いれば、同時入力は起きる。
注文を受けたその場で入れる運用なら、なおさら重なる。

今の構成は JSON ファイル1枚なので、後から書いた方が前を上書きし、数字が飛ぶ。

### 今回やること（最低限）

書き込む直前にファイルを読み直す。
自分が読んだ時から変わっていたら、上書きせず止める。

```
「他の方が先に入力したようです。もう一度お願いします」
```

数字が飛ぶことだけは防げる。実装は数十行。

### 今回やらないこと

本格的なロック機構は作らない。JSON で頑張る話ではない。
譲渡・本番運用の段階で DB（SQLite / PostgreSQL）に移す時に、DB 側に任せる。

## 9. 入力の入り口

| 方式 | 実装の重さ | 効果 | 状態 |
|---|---|---|---|
| **チャット UI（Web）** | — | 大 | **実装済み** |
| CLI | — | 中 | **実装済み**（UI と同じ計算層を呼ぶ） |
| メモ貼り付け | 軽 | 大 | **1**（UI・CLI どちらからでも） |
| CSV / スプレッドシート | 中 | 中 | 2 |
| メニュー表スキャン | 軽（画面不要だった） | 大 | 実装済み（UI・CLI どちらからでも） |
| 納品書スキャン | — | 小 | 個別実装は不要（同じ経路で渡せる） |

### チャット UI と CLI（同じ計算層）

当初は CLI のみとしていたが、開発中にチャット形式の Web UI を追加した。
理由は、エージェントであることが対話の形でしか伝わらないため。

**UI と CLI は同じ Python ツール群を呼ぶ。**
表示の入り口が2つあるだけで、計算は一箇所にしかない。

- 計算ロジックを JavaScript 側に持たせない
- `state.json` の書き込みガード（§7 同時書き込み）は UI 経由でも同じく効く
- UI から呼べる操作は CLI から呼べる操作と同一。UI 限定の機能を作らない

この分離が崩れると、UI と CLI で違う数字が出る。
そうなった時点で、どちらの数字も信用できなくなる。

### メモ貼り付け（record_purchase）

書式を決めない。1行でも10行でも読む。

```
店主「肉A 1本、ピタ 100枚、ソース 3本、ナプキン 1000枚」
→ 読み取って「これで合っていますか」と確認を返す
```

CLI のまま動く。画面が要らない。

### メニュー表スキャン

読み取り後は必ず確認を出す。黙って登録しない。

```
「読み取りました。合っていますか」
 ケバブサンド ¥600
 ケバブラップ ¥600
```

実装した結果、画面は要らなかった。CLI の行にファイル名を打てば、写真も
表計算ファイルも渡せる（`attachments.py`）。モデルが直接読むため、
表計算ライブラリもOCRも使っていない。納品書も同じ経路で渡せるので、
「納品書スキャン」を別途作る必要はなくなった。
Web UI では、ファイルをドロップするか添付ボタンで同じ経路に入る。

**読み取れるのは `product` と `price` だけ。**
`qty`（肉75g）はメニュー表のどこにも書かれていない。
`unit_type` と `tier` も同じで、
「盛り付ける時、毎回同じ量になりますか」の答えでしか決まらない。
入力の省力化には効くが、**カウンセリングの代替にはならない。**

もっともらしい読み違いには気づけない。字が潰れて読めない失敗は気づけるが、
誤読した「1,200円」は気づけない。税抜・税込の併記、「大盛り +100円」のような
オプション行の誤認も起きる。読み取り後に必ず確認を出すのはそのためで、
黙って登録してはいけない。

## 11. 油の扱い（Tier 3）

かつては別途設計が必要だったが、消費型の3分類（第2章）でユニット型に吸収された。

- 継ぎ足しは本（缶）単位
- フライヤーは一斗缶または規定量で1サイクルとして回す
- 「減った量」より「交換からの経過」「揚げた回数」で判断する

このロジックは**ユニット型そのもの。** 油だけの特殊処理ではなくなった。
デモの初期データには含めない（実装は consumption_type: unit を使う）。

## 12. メモ（今回の範囲外）

- 乾物・調味料の廃棄目安。シーズニングはスパイス単体より劣化が早い
- 単位系の換算（g ↔ oz、L ↔ gal）。unit_type があれば後付け可能
- 「新人が入ったら係数がリセットされる」という考え方
- 「1本 = 何g」の平均も、係数と同じ仕組みで学習できる
