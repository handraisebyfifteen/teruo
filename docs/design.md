# 設計書A — キッチンカー在庫エージェント

> English translation: [design.en.md](design.en.md)

Tier 1（初期実装）の実装元は、ユーザー提供の設計書
`Pasted--A-0-Replit-Agent--1788164012029_1788164012029.txt` です。
本書はそれを引き継ぎ、Tier 2〜4 への拡張を定義します。

インターフェースは引き続きターミナルで動くCLIのみです。
Web UI、データベース、発注の自動化、メール、天気、認証は対象外です。
「通知」はすべてCLI上の表示（起動時と `check_alerts` 実行時）を指します。

**共通原則: いずれの Tier も、数値計算はすべて Python 側（ツール）で行い、
AI に暗算させない。** エージェントはツールの呼び出しと結果の伝達のみを行います。

---

## 1. Tier の分類

| Tier | 性質 | 例 | 管理方法 |
|------|------|----|----------|
| 1 | 減る・レシピに比例・回転が速い | ソーセージ、パン | レシピ×係数で引き算、棚卸しで係数補正 |
| 2 | 減る・人と客で変わる・回転が速い | ケチャップ、マスタード | 「1本で何食いけるか」で引き算、確信度が早く下がる |
| 3 | 減る・計算で読める・回転が遅い | 包み紙、ガスボンベ、揚げ油 | 精度を追わず、リードタイム＋安全在庫で守る |
| 4 | 減らない・期日が来る | 点検、支払い、営業許可の更新 | 消費計算なし。期日で通知 |

## 2. エンジンの分割

エンジンは2つに分け、それぞれ独立したモジュールにします。

- **消費エンジン**（`consumption.py`）: Tier 1〜3 を担当。
  オーダー（売上）と営業日から在庫を引き算する。棚卸しによる補正、
  確信度の算出、Tier 3 の残り日数計算もここに置く。
- **カレンダーエンジン**（`calendar_engine.py`）: Tier 4 を担当。
  消費計算を一切行わず、期日とリードタイムだけで通知を判定する。
  （ファイル名は標準ライブラリ `calendar` との衝突を避けて `calendar_engine.py` とする）

`tools.py` はエージェントに公開する薄いラッパーに徹し、計算ロジックは
両エンジンに移します（Tier 1 の既存ロジックも `consumption.py` へ移動）。

```
main.py             — CLI・エージェント定義・起動時アラート表示
tools.py            — エージェント公開ツール（薄いラッパー）
consumption.py      — 消費エンジン（Tier 1〜3）
calendar_engine.py  — カレンダーエンジン（Tier 4）
store.py            — 永続化（変更なし）
data/state.json     — 状態
```

## 3. 営業日の扱い

- **営業日 = 売上が1件以上記録された日付** とする。
- `record_sales` で新しい日付の売上が初めて記録された時点で1営業日と数え、
  Tier 3 の「1営業日あたり」品目をその場で減算する。
- 二重減算を防ぐため、処理済みの営業日を `state.json` の
  `business_days` 配列（日付文字列のリスト）に記録する。
- 制約: 売上ゼロの営業日は自動では数えられない（実運用上まれなので許容する）。

## 4. 確信度（Tier 1・2）

「計算上の在庫がどれだけ信用できるか」を、最終棚卸しからの経過営業日数から
**導出**する（保存はしない。保存値とのズレを防ぐため）。

```
確信度 = max(0, 1 − 経過営業日数 / D) × 100 (%)
```

- D は Tier ごとの定数（コード内定数）: **Tier 1 = 20営業日、Tier 2 = 7営業日**。
  Tier 2 は人と客で使用量が変わり係数の変動が大きいため、早く下がる。
- 確信度が **30% 未満** になったら「棚卸し推奨」アラートを出す。
- Tier 3 は確信度を持たない（回転が遅く係数が育たないため、精度を追わない）。

## 5. Tier 別の設計

### Tier 1（既存・変更点のみ）

計算方法は現行実装のまま（レシピ×係数、棚卸しで係数補正、補正幅 0.8〜1.5 倍）。
変更点は次の2つ。

1. 確信度の表示・アラート対象になる（§4）。
2. 係数補正の実消費の計算に入荷を含める（§6 `record_restock` の導入に伴う）:
   `実消費 = 前回実測 + 期間中入荷 − 今回実測`

### Tier 2 — 減る・人と客で変わる・回転が速い

- 消費量は **「1本で何食いけるか」**（`servings_per_unit`）で持つ。
  例: ケチャップ 1本で50食。
- 商品レシピに Tier 2 品目を追加し、`qty` は「1食あたりの食数換算」（通常 1）。
- 売上 N 食あたりの消費: `N × qty ÷ servings_per_unit` 本。
- 棚卸し時の補正（消費エンジンが計算）:
  ```
  提供食数 S     = 前回棚卸し以降の対象売上の合計食数
  実消費（本）   = 前回実測 + 期間中入荷 − 今回実測
  新しい servings_per_unit = S ÷ 実消費
  ```
  変動が大きい前提なので、補正幅は現行値の **0.5〜2.0 倍**にクランプする
  （Tier 1 の 0.8〜1.5 より広い）。実消費が 0 以下のときは補正しない。
- 確信度は D=7営業日 で減衰（§4）。

### Tier 3 — 減る・計算で読める・回転が遅い

- 消費単位は **2種類を許す**。品目ごとに `consumption` フィールドで宣言する:
  - `{"type": "per_order", "qty": 1}` — 1オーダーあたり（例: 包み紙 = 1枚）。
    `record_sales` 時に `売上食数 × qty` を減算。レシピには載せず、
    全商品共通で食数に比例させる。
  - `{"type": "per_business_day", "qty": 0.4}` — 1営業日あたり（例: ガスボンベ = 0.4本）。
    新しい営業日の初回売上時に `qty` を減算（§3）。
- **係数補正は行わない**（回転が遅く係数が育たないため、精度を追わない）。
  棚卸しは在庫の上書きのみ。
- **リードタイムと安全在庫で守る**。品目ごとに
  `lead_time_days`（発注から届くまでの日数）と `safety_days`（安全余裕日数）を持つ。
- 残り日数（営業日ベース）の計算:
  - per_business_day: `残り日数 = stock ÷ qty`
  - per_order: `残り日数 = stock ÷ (直近14営業日の平均消費量/営業日)`。
    平均が 0 のときは「算出不可」と表示し、アラートは出さない。
- **`残り日数 ≤ lead_time_days + safety_days` になったら発注アラート**を出す。
  残り日数は営業日、リードタイムは暦日だが、営業日残り ≦ 暦日残りなので
  この比較は常に安全側に倒れる（早めに鳴る）。

### Tier 4 — 減らない・期日が来る

- **消費計算を一切行わない**。カレンダーエンジンのみが扱う。
- 持つデータは次の **4つ**:

  | フィールド | 意味 | 例 |
  |---|---|---|
  | `next_due` | 次回期日（YYYY-MM-DD） | 2026-11-01 |
  | `cycle` | 周期。`{"months": n}` か `{"days": n}` のどちらか | `{"months": 6}` |
  | `lead_time_days` | 期日の何日前から準備が要るか | 14 |
  | `impact` | 遅れた場合の影響（自由テキスト） | 「営業停止」 |

- **`今日 ≥ next_due − lead_time_days` になったら期日アラート**を出す
  （impact を併記して重みが伝わるようにする）。期日超過はさらに強調表示。
- 完了記録（`record_task_done`）で `next_due = 現在の next_due + cycle` に更新する
  （予定日基準。支払いのように周期が固定のものに合う）。
  点検のように完了日基準にしたい場合や大幅に遅れた場合のために、
  `record_task_done` は任意引数で次回期日の直接指定を許す。

## 6. ツール一覧

| ツール | 対象 | 内容 |
|---|---|---|
| `record_sales(date, product_id, quantity)` | Tier 1〜3 | 【拡張】Tier 1 に加え、Tier 2（レシピ経由）と Tier 3 per_order を減算。新しい営業日なら per_business_day も減算し `business_days` に記録 |
| `record_count(item_id, actual_stock)` | Tier 1〜3 | 【拡張】Tier 1 は係数補正、Tier 2 は servings_per_unit 補正、Tier 3 は上書きのみ。いずれも `last_counted` を更新 |
| `record_restock(item_id, quantity, date)` | Tier 1〜3 | 【新規】入荷を記録し在庫を加算。`restocks` に履歴を残す（入荷を記録しないと Tier 3 の残り日数と Tier 1・2 の係数補正が成立しないため必須） |
| `get_stock_status()` | 全Tier | 【拡張】Tier 1・2: 在庫・係数・確信度。Tier 3: 在庫・残り日数。Tier 4: 次回期日・残り日数・impact |
| `record_task_done(task_id, date, next_due=None)` | Tier 4 | 【新規】完了を記録し次回期日を周期で更新（next_due 指定時はそれを優先） |
| `check_alerts()` | 全Tier | 【新規】棚卸し推奨（確信度<30%）、発注アラート（Tier 3）、期日アラート（Tier 4）をまとめて返す。`main.py` が起動時にも直接呼んで表示する |

## 7. データモデル（state.json）

既存キーはそのまま、フィールドとキーを追加します。既存データの移行は
「新フィールドがなければデフォルト扱い」で吸収し、変換スクリプトは作りません。

```json
{
  "products": [
    {
      "id": "hotdog",
      "name": "ホットドッグ",
      "recipe": [
        { "item_id": "sausage", "qty": 1 },
        { "item_id": "bun", "qty": 1 },
        { "item_id": "ketchup", "qty": 1 }
      ]
    }
  ],
  "items": [
    {
      "id": "sausage", "name": "ソーセージ", "tier": 1,
      "unit": "本", "stock": 3000.0,
      "coefficient": 1.0, "last_counted": "..."
    },
    {
      "id": "ketchup", "name": "ケチャップ", "tier": 2,
      "unit": "本", "stock": 4.0,
      "servings_per_unit": 50, "last_counted": "..."
    },
    {
      "id": "wrapper", "name": "包み紙", "tier": 3,
      "unit": "枚", "stock": 800.0,
      "consumption": { "type": "per_order", "qty": 1 },
      "lead_time_days": 3, "safety_days": 2, "last_counted": "..."
    },
    {
      "id": "gas", "name": "ガスボンベ", "tier": 3,
      "unit": "本", "stock": 5.0,
      "consumption": { "type": "per_business_day", "qty": 0.4 },
      "lead_time_days": 5, "safety_days": 3, "last_counted": "..."
    }
  ],
  "tasks": [
    {
      "id": "extinguisher", "name": "消火器点検",
      "next_due": "2026-11-01", "cycle": { "months": 6 },
      "lead_time_days": 14, "impact": "営業停止"
    }
  ],
  "history": [ { "date": "...", "product_id": "...", "quantity": 0, "recorded_at": "..." } ],
  "restocks": [ { "date": "...", "item_id": "...", "quantity": 0, "recorded_at": "..." } ],
  "business_days": [ "2026-08-30", "2026-08-31" ]
}
```

- `items` は Tier ごとに持つフィールドが異なる。Tier 4 は `items` ではなく
  `tasks` に置き、消費エンジンからは見えない。
- 定数（確信度の D、クランプ幅、per_order 平均の窓 14営業日、
  アラート閾値 30%）はコード内定数とし、state.json には持たない。
