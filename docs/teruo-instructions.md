# teruo — 指示書（Claude Code 向け・ステップ0〜6）

## 0. この指示書の使い方

### 一度に全部渡さない

該当ステップの節だけを切り出して Claude Code に渡すこと。
全文を一度に渡すと、前のステップの検証を飛ばして先に進み、
どこが壊れたのか分からなくなる。

各ステップの冒頭に「着手の条件」がある。満たすまで次に進まない。

### 書かれていないことをやらない

Replit Agent も Claude Code も、放っておくと Web 画面と DB を足す。
以下はこの先も作らない。

- Web 画面、HTML、React、Flask / FastAPI
- データベース（PostgreSQL / SQLite / Firestore 含む）
- Docker
- 認証・ユーザー管理（合言葉は認証ではない。ステップ4参照）
- 天気 API、外部データの取得

### 既にあるものを作り直さない

各ステップの作業に入る前に、まずその機能が既に存在するか確認する。

- 既にあり、設計書通りに動く → 触らない
- 既にあるが、設計書と違う → 差分だけ直す。全面書き直しをしない
- ない → 新規に作る

動いていたものを作り直して壊すのが、この工程で一番損失が大きい。
判断に迷ったら、実装せずに chaosprank に確認する。

### 各ステップの終わりに差分レポート

```
■ 設計書との相違
  該当箇所 / 設計書の記述 / 実際の実装 / 相違が生じた理由

■ 判定
  実装を直すべきか、設計書を直すべきか

■ 修正案
```

実装してみて設計が誤っていたと分かった場合は、設計書側を更新する。
設計書は一方通行ではない。

### 審査を意識した優先順位

審査項目は5つ（技術・デザイン・インパクト・独創性・プレゼン）。

- **独創性・インパクトは既に強い** ← 現場経験、弾込め、寿司28g
- **技術で戦う手当てが 1.5 と 5.5** ← 「動く」だけでなく「正しい」を示す
- **プレゼン（6）を削ると、他が良くても届かない**

### 1-3. history に venue_type を追加する

```json
{
  "recorded_at": "2026-09-01T20:14:00+09:00",
  "venue_type": "solo",
  "product_id": "kebab_sand",
  "quantity": 35
}
```

- 値は "event" または "solo" の2択のみ
- record_sales に引数 venue_type を追加
- 省略時は "solo" を既定値とする（毎回聞くと入力が止まる）

#### 背景（実装者向け）

イベント出店は来場者数が事前に分かるため見込みが立つ。
単独出店（マルシェ等）は母数も競合も不明。
混ぜて平均を取ると両方外れる。
今回は記録するだけ。平均の分離はステップ5。

### 1-4. 同時書き込みで数字が飛ぶのを防ぐ

在庫担当が2人いれば同時入力は起きる。
JSON ファイル1枚なので、後から書いた方が前を上書きする。

state.json を書き込む直前に、ファイルをもう一度読む。
自分が読み込んだ時点の内容から変わっていたら、上書きせず中断する。

```
「他の方が先に入力したようです。もう一度お願いします」
```

- 判定は mtime またはハッシュでよい
- 本格的なロック機構は作らない。数字が飛ぶことだけ防げれば十分
- 本番運用で DB に移す際、DB 側に任せる

### 1-5. 単位を直書きしない

- unit_type は weight / volume / count のいずれか
- コード内に「g」「枚」を直書きしない。すべて item["unit"] を参照する
- これがないと、後から oz や lb を足す時に全面書き直しになる

## ステップ1.5 — 係数の収束を検証する

**着手の条件**: ステップ1の完了条件を満たしていること。

**なぜここでやるか**: この後のステップで計算層に手が入る。
先に検証の仕組みを作っておけば、変更しても壊れていないことを確認できる。
逆順にやると、壊れても気づけない。

**審査上の位置づけ**: 「動く」だけでなく「正しいことを示している」は
技術的実装の評価で効く。動画に貼れる絵になる。

### 1.5-1. 何を検証するか

teruo の中核の主張は「手の誤差を学習する」こと。それが本当かを実データで示す。

```
1. 「真の係数」を決める（現場では、レシピと違う量が実際に使われている状態）
2. 20営業日ぶんの売上と棚卸しを、その係数で機械的に生成する
3. teruo（実ツールの record_sales / record_count）に順番に食わせる
4. 係数が 1.0 から真の値に近づくかを見る
```

シナリオは2つ。上限（レシピ±4g/食）の**内側**（例: 1.04 → 収束するはず）と
**外側**（例: 1.15 → 上限で止まり警告が出るはず。原則12の検証）。

### 1.5-2. 実装

`tests/simulate_convergence.py` として置く。**本体のコードは変更しない。**

- 既存の record_sales / record_count をそのまま呼ぶ
- state は本番と別ファイル（tests/sim_state.json）を使う
- 実際の消費量は `理論値 × 真の係数 × ばらつき（±5%程度）`
  — 現場では毎日ぴったり同じ量にはならない
- 出力: 棚卸し回数ごとの係数の CSV とグラフ（matplotlib / PNG。
  横軸=棚卸し回数、縦軸=係数、真の係数の水平線を引く）

### 1.5-3. 確認項目

- [ ] 係数が 1.0 から真の値に向かって動く
- [ ] 5回前後で概ね収束する
      → しなければ設計書の「学習中は棚卸し5回まで」が誤り。実測に合わせて直す
- [ ] ばらつきがあっても係数が振動し続けない
      → 振動するなら更新式に平滑化を入れ、設計書に反映する
- [ ] 紙類（1食1枚の品目）の係数は 1.0 のまま動かない
- [ ] 本番の data/state.json が書き換わっていない

### 1.5-4. 収束しなかった場合

**それも成果。** 隠さず報告する。「5回で収束」は設計時の仮定であって検証結果ではない。
実際に7回かかるなら、設計書側を実測値に書き換える。数字を実測に合わせるのが正しい順序。

### 検証結果（2026-09-01 実施）

- 生の更新式（実測を全量採用）は日々のブレを追いかけて**±5%で振動した**
  → 更新式に平滑化（実測へ半分ずつ寄せる）を入れた。設計書2章に反映済み
- 平滑化後: 3〜5回で収束、5回目以降の平均は真の値との差0.6%、振れ幅±2.6%
- 上限超えシナリオは上限で止まり、毎回警告が出た（原則12どおり）
- 紙類（count型）は 1.0 のまま
- 出力: tests/convergence.csv / tests/convergence.png

## ステップ2 — 登録・編集ツール

**着手の条件**: ステップ1の完了条件をすべて満たしていること。
係数が動かないまま先に進まない。

### 2-1. 追加するツール（6つ）

| ツール | 役割 | 権限 |
|---|---|---|
| register_item | 品目を追加（名前・単位・在庫） | 店主のみ |
| register_product | 商品を追加（名前・レシピ） | 店主のみ |
| update_recipe | レシピの数量を修正 | 店主のみ |
| update_item | 品目の名前・単位を修正 | 店主のみ |
| delete_product | 商品を削除 | 店主のみ |
| record_purchase | 仕入れ記録 | 在庫担当 |

品目の削除ツールは作らない（設計書 原則5）。
使わなくなった品目は active: false にするだけ。在庫と履歴が繋がっているため、
消すと過去が壊れる。

### 2-2. register_item

必須は3つだけ。

- 名前
- 単位（unit と unit_type）
- 現在の在庫

聞かないもの

- tier — エージェントが性質から判断して仮で置く
- coefficient — 必ず 1.0 から始める。店主に決めさせない

purchase_unit / unit_weight は、仕入れ単位が消費単位と違う場合のみ聞く。

```
「肉はどう仕入れますか。塊ですか、パックですか」
→ 塊 →「1本だいたい何kgですか」→ unit_weight
→ パック → purchase_unit も unit_weight も持たせない
```

### 2-3. register_product

品目が存在しないと商品は作れない。だが店主に順序を意識させない。

```
店主「ケバブサンド追加して。ピタ1枚と肉75g」
→「ピタパンとケバブ肉はまだ登録されていません。先に登録しますか」
→ 裏で register_item を2回、その後 register_product
```

店主から見れば1回の会話。

量が決まっていない材料は AI が埋める

```
店主「サンドはピタと肉とキャベツとソース」
→「キャベツ30g、ソース20gで置いておきます。後で直せます」
```

空欄で止めない。止まると店主が離脱する。
埋める値は店の性格を踏まえる（日本の屋台なら量は控えめ）。

### 2-4. update_item（単位変更の扱い）

単位を変える操作は特別扱いする。

- 同種別（g → kg）は換算する
- 種別をまたぐ（g → 本）は換算しない。棚卸しで入れ直してもらう

```
「肉の単位を g から 本 に変えますか。
 現在の在庫 5,200g は数え直しが必要です。
 いま何本ありますか」
```

単位変更時に必ず行うこと

- 変更前の単位・在庫・日時を history に残す
  → 過去の数値が「どの単位で記録されたか」を後から追えるようにする
- その品目の coefficient を 1.0 に戻す
  → 単位が変われば係数の意味も変わる。引き継いではいけない
- 育成期として扱い直す（count_history はクリアしない、記録は残す）

### 2-5. delete_product

- 確認必須。一度で消さない
- 商品を消しても、品目は消さない
- history は消さない

### 2-6. record_purchase（メモ貼り付け）

書式を決めない。1行でも10行でも読む。

```
店主「肉A 1本、ピタ 100枚、ソース 3本、ナプキン 1000枚」
→ 読み取って「これで合っていますか」と確認を返す
→ 承認されたら在庫に加算
```

「1本 = 何g」の扱い

- 実測が言えれば、それを使う → 在庫にその値を加算
- 言えなければ unit_weight の目安値で仮置き
- 棚卸しの実測が来たら、そちらが常に勝つ（設計書 原則2）

```
店主「肉、1本入った。3,850gだった」
→ 在庫に 3850 を加算
→ unit_weight の実績として記録（平均を更新）

店主「肉、1本入った」
→ 目安値 10000 で仮置き
→「実際の重さが分かれば教えてください。棚卸しでも直せます」
```

### 2-7. CSV / スプレッドシート読み込み

余裕があれば。優先度は低い。メモ貼り付けで代替できる。

納品書スキャンは実装しない。メモ貼り付けで足りる。

### ステップ2の完了条件

```
> 品目を追加したい。ヨーグルトソース、g、3000gある
  → register_item が動く。coefficient は 1.0

> ケバブサンドにソース20g足して
  → update_recipe が動く

> ソースの単位を本に変えたい
  → 確認が出る。history に変更前が残る。係数が 1.0 に戻る

> 肉、1本入った。3850gだった
  → 在庫に加算される。unit_weight の実績が記録される

> ケバブミートのみを削除して
  → 確認が出る。承認後、商品だけ消える。品目は残る
```

- [ ] 6ツールすべてが動く
- [ ] 品目の削除ツールが存在しない
- [ ] 単位変更で係数が 1.0 に戻る
- [ ] 単位変更の履歴が残っている
- [ ] history が一度も消えていない

## ステップ3 — 初回カウンセリング

**着手の条件**: ステップ2の完了条件を満たしていること。

このステップはコードがほとんど要らない。9割はシステムプロンプト。

### 3-1. 設計の原則

#### 業種名で決め打ちしない

「ケバブ屋だからこの構成」としない。作り方を聞いて判定する。

同じ「アイス屋」でも、スクープ式（誤差が出る）と棒アイス（誤差ゼロ）で
まったく性質が違う。業種テンプレートは作らない。

#### 完璧に埋めさせない

- 全7段階で10分以内
- 途中でやめても、そこまでが保存される
- 後から register_item で足せる

### 3-2. 段階1 — 店の輪郭

```
「どんなものを売っていますか」
「メニューをひと通り教えてください」
```

業種名を聞いても、内部では決め打ちしない。

### 3-3. 段階2 — メニューごとの中身

```
「ケバブサンドには何が入りますか」
→ ピタ、肉、キャベツ、ソース

「量が決まっているものはありますか」
→ 肉75g

「残りはこちらで置いておきます。キャベツ30g、ソース20g。後で直せます」
```

空欄で止めない。AI が埋めて先に進む。

### 3-4. 段階3 — 誤差を聞く（tier 判定）

この一問が tier を決める。

```
「盛り付ける時、毎回同じ量になりますか。人によって変わりますか」
```

| 答え | 判定 |
|---|---|
| 変わらない（袋から出す、1本渡す） | Tier 1・係数は 1.0 固定 |
| 変わる（すくう、削ぐ、かける） | Tier 1 だが係数が動く / Tier 2 |

### 3-5. 段階4 — 見落としを拾う（★このリストが本システム最大の資産）

店主は材料しか言わない。「他にありますか」では絶対に出てこない。
エージェントから具体的に聞きにいく。

```
「揚げ物はありますか」          → 油
「持ち帰りの容器は」            → 容器、袋、ナプキン
「割り箸やスプーンは」          → カトラリー
「ドリンクは出しますか」        → カップ、蓋、ストロー
「ラップ紙や敷き紙は」          → 紙類
「ビニール袋は」                → レジ袋
```

★ この節は要拡充。現場経験からリストを増やすこと。
ここが他の実装との差になる部分。想像で書くと必ず抜ける。

### 3-6. 段階5 — 仕入れの単位

```
「肉はどう仕入れますか。塊ですか、パックですか」
→ 塊 →「1本だいたい何kgですか」→ unit_weight に入る
```

#### 参考：ケバブ肉の実際の流通（調査済み）

- ホール（塊）は 10kg / 15kg / 20kg / 25kg / 30kg で流通。kg単価850円前後
- キッチンカーはグリルのサイズから 10〜15kg が現実的
- 調理・カット済みを 1kg 真空パックで卸す業者もある（誤差ほぼゼロ）

→ 同じ品目でも店によって仕入れ形態が違う。
　 だから purchase_unit / unit_weight は店主が設定できる必要がある。

### 3-7. 段階6 — 現在庫

```
「今ある分を教えてください。だいたいで大丈夫です」
```

正確さを求めない。求めると始められない。棚卸しで直る。

### 3-8. 段階7 — 合言葉と通知先

```
「レシピや単位を変える時だけ使う合言葉を決めてください。
 日々の入力には要りません。
 スタッフの方が誤って設定を変えてしまうのを防ぐためです」

「設定が変わった時にお知らせするメールアドレスを教えてください。
 合言葉を知っている人が増えても、変更に気づけるようにするためです」
```

メールアドレスは state.json に持つ。
リポジトリ公開時にデモ用の架空アドレスに差し替えること。

### 3-9. 最後に必ず言うこと（設計書 原則9）

```
「最初の1〜2週間は、こちらが数え方を覚える期間です。
 数字は参考程度に見てください。
 何度か棚卸しをしてもらえれば、精度が上がっていきます」
```

先に言っておくから信用される。外れてから言うのは言い訳になる。

## ステップ4 — 合言葉と変更通知

**着手の条件**: ステップ3の完了条件を満たしていること。

時間が足りなければ簡易版（4-4）に切り替える。
ステップ5・6を優先する。

### 4-1. 権限の3層

| 層 | 誰 | できること |
|---|---|---|
| 店主 | オーナー | 全部。構造変更には合言葉が要る |
| 在庫担当 | 任された上位スタッフ | 売上・棚卸し・仕入れの入力 |
| 一般 | それ以外 | 触らない |

「誰でも」ではない。入ったばかりの人は在庫入力をしない。

### 4-2. 操作ごとの扱い

| 操作 | 誰が | 実行前 | 実行後 |
|---|---|---|---|
| 売上を入れる | 在庫担当 | — | — |
| 棚卸しを入れる | 在庫担当 | — | 異常値の時のみ通知 |
| 仕入れを入れる | 在庫担当 | — | — |
| レシピの量を変える | 店主のみ | 合言葉＋確認 | 通知 |
| 単位を変える | 店主のみ | 合言葉＋確認 | 通知（変更前後の値つき） |
| 品目を追加する | 店主のみ | 合言葉＋確認 | 通知 |
| 商品を削除する | 店主のみ | 合言葉＋確認 | 通知 |

#### なぜ2段構えか

合言葉は入口の鍵で、通知は後から気づく手段。
役割が違うので両方要る。

合言葉は必ず漏れる。店主が忙しくて従業員に教える、人が入れ替わって全員が知っている、
という状態は現実に起きる。その時に残る最後の防波堤が通知。

合言葉は認証ではない。防げるのは「うっかり」だけ。
本格的な権限管理は本番運用で足す。

### 4-3. 通知の中身

```
【設定が変更されました】
2026-09-01 14:32

ケバブサンドのレシピ
  ケバブ肉（チキン） 75g → 90g

心当たりがない場合はご確認ください。
```

- 変更前と変更後を両方書く。「変更されました」だけでは何が起きたか分からない
- 変更を止める機能は作らない。通した上で知らせる。
  止めると、店主の返事待ちで現場が止まる
- 元に戻す操作は店主が手で行う（history に変更前が残っているため可能）

送信手段はメール。LINE / Slack は連携の手間が締切に合わないため見送り。

### 4-4. 間に合わない場合の簡易版

メール送信は SES の設定が要り、AWS 側の作業が増える。
締切に響くなら、通知の代わりに履歴表示だけにする。

- 「設定変更の履歴」を get_stock_status から見られる形にする

これで「誰かが設定を変えたことが後から分かる」という目的の8割は達成できる。
実装は30分。

### ステップ4の完了条件

- [ ] 構造変更5ツールが合言葉を求める
- [ ] 日々の入力4ツールは合言葉を求めない
- [ ] 変更前後の値が両方記録される
- [ ] 通知（またはその簡易版）が動く
- [ ] 合言葉がコードに直書きされていない

## ステップ5 — 育成フェーズと報告タイミング

**着手の条件**: ステップ4（簡易版可）が終わっていること。

ここがデモの目玉。実装は軽いが、効果は大きい。

### 5-1. 育成フェーズの表示

導入直後と2週間後では信頼度が違う。それを店主に見せる。

```
1週目「学習中です（棚卸し 2回目 / 5回）。数字は参考程度に見てください」
2週目「チキンの係数が安定してきました」
3週目「在庫、そろそろ切れます」← ここから発注提案を始める
```

実装は count_history の件数と係数の変動幅を見るだけ。

#### 「学習中」には期限を設ける

1ヶ月経っても「学習中です」と言い続けるなら、それは学習していないのと同じ。
そして「学習中」は言い訳の逃げ道になる。数字が外れても済ませられてしまう。

- 期限は 2週間、または棚卸し5回。どちらか早い方
- 期限を過ぎたら、精度が上がっていなくても「学習中」とは言わない
- 代わりになぜ安定しないかを報告する

```
×「まだ学習中です」          ← 言い訳

○「チキンの数字が安定しません。
   考えられるのは、削る人が日によって違う、
   棚卸しのタイミングがまちまち、のどちらかです」  ← 情報
```

#### 途中経過を必ず出す

終わりが見えない学習中は不安なだけ。残りを見せる。

```
「学習中です（棚卸し 2回目 / 5回）」
```

### 5-2. 報告のタイミング

営業中は原則、黙る。

#### なぜ営業中に言わないか

在庫が切れるのは、必ず一番忙しい時。その最中に言われても対応できない。
対応できない情報は邪魔でしかない。

そしてピークが引いた瞬間も暇ではない。
次の山に向けた**「装弾」の時間**（肉を刺す、野菜を切る、ソースを詰める）であり、
むしろ手が空かない。「引いたら入力」は成立しない。

#### 3つのタイミング

| いつ | 何を言うか |
|---|---|
| 開店前 | 今日の見込み。足りないものの予告 ← ここが本命 |
| 営業中 | 原則、黙る。切迫時のみ「あと10食分」と事実だけ |
| 締め | 実績、棚卸しの依頼、発注 |

開店前が唯一、判断できる時間。手が空いていて、まだ買い足せる。
営業中は手遅れ、締めはもっと遅い。

#### 営業中に言っていいこと

事実のみ。判断を求めない。

```
○「ソース、あと10食分です」
×「ソース、あと10食分です。発注しますか？」
×「どうしますか？」
```

あと10食と分かれば、その場でできることがある
（量を減らす、メニューから外す、告知する）。判断は一瞬で済む。

### 5-3. 入力の頻度を強制しない

打てる時に打つ。打てなければ締めでいい。
システム側が入力の頻度に合わせて振る舞いを変える。

```
締めの入力しかない日が続いたら
→「日中は打てないようですね。締めだけで大丈夫です」
→ 締めのデータから翌日の見込みを立てる方に切り替える
```

「その都度入れてください」と要求しない。

### 5-4. 棚卸しの頻度

システムが一律に決めない。店主にも決めさせない。必要な時だけ頼む。
毎日全部数えさせたら3日でやめる。

| 時期 | 頻度 | 言い方 |
|---|---|---|
| 育成期（最初の5回程度） | 営業後に毎回 | 「まだ覚えている途中なので、今日も数えてもらえますか」 |
| 安定後 | 週1 | 「チキンは安定したので、来週まで数えなくて大丈夫です」 |
| 臨時 | その都度 | ズレが大きい / 新しい人が入った / 切れそう |

#### 全部を一度に数えさせない

20品目あっても、その日に頼むのは2〜3品目だけ。
何を数えるか選ぶのがエージェントの仕事。

### 5-5. venue_type で平均を分ける

ステップ1で記録した venue_type を、ここで使う。

- イベントと単独で平均を別々に持つ
- 混ぜて平均を取ると両方外れる

#### 仕込み量の扱い（重要）

仕込みの量は「気合の量」であり、会場の規模を表している。

- イベントで多く仕込むのは正常
- 単独出店で仕込みが多い日だけが読み違い

仕込み量を単独で判断材料にしない。必ず出店形態とセットで見る。

### 5-6. 守るのは在庫だけ（設計書 原則8）

- 在庫の残量は辛めに見る。切れる予測は早めに出す
- 売上の見込みは辛くしない。売れるかどうかは店主の領分

「今日は行ける」と思っている人に対して、在庫計算まで同じ楽観で回すと、
外れた時に何も残らない。だが売上まで悲観的に言うのは越権。

### ステップ5の完了条件

- [ ] 棚卸し回数が「2回目 / 5回」の形で表示される
- [ ] 5回（または2週間）を過ぎたら「学習中」と言わなくなる
- [ ] 安定しない時、原因の候補を挙げる
- [ ] 営業中に「どうしますか」と聞かない
- [ ] 一度に頼む棚卸しが2〜3品目に絞られている
- [ ] event / solo で平均が分かれている

## ステップ5.5 — エージェントを役割で分ける

**着手の条件**: ステップ5の完了条件を満たし、
かつステップ1.5の収束グラフが出せる状態であること。

**分けた後、必ずステップ1.5のシミュレーションを再実行し、
係数が同じ結果に収束することを確認する。** 壊れていないことの唯一の担保。

### 5.5-1. なぜ分けるか

正直に書く: 技術的な必然性は薄い。1つのエージェントでも同じ動作はできる。

ただ、Strands Agents SDK はマルチエージェント連携を主要機能としており、
単一エージェント＋ツールだけでは SDK を使った意味が伝わりにくい。
加えて、**分割の線が設計と一致している**。無理に足すのではなく、
既に設計書にある3つの判断を、そのまま3つのエージェントにするだけ。

### 5.5-2. 3つの役割

| エージェント | 仕事 | 設計書の対応 |
|---|---|---|
| **記録係** | 売上・棚卸し・仕入れを受け、Python ツールで計算する | 原則3「計算は Python」 |
| **観測係** | 異常を見つける。今日どの品目を数えてもらうか選ぶ | 4章「全部を一度に数えさせない」 |
| **報告係** | いつ何を言うか決める。営業中は黙る | 5章「報告のタイミング」 |

- 記録係は判断をしない。数字が変でもそのまま記録する（異常判定は観測係）
- 観測係は係数の変動幅を見て安定/未安定を判定し、今日頼む棚卸しを2〜3品目に絞る
- 報告係は開店前/営業中/締めの3タイミングを守り、営業中は切迫時のみ事実だけ

### 5.5-3. 実装方針

- Python のツール群（計算層）と state.json の構造、係数の更新式は**一切変更しない**
- 上に乗る判断層だけを3つに分ける
- Strands Agents SDK のエージェント間連携の作法に従う
  → **SDK のドキュメントを確認してから実装すること。**独自にプロセス間通信を組まない
